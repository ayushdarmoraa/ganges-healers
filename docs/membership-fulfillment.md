# Membership checkout and fulfillment

Real `POST /api/memberships/subscribe` requests require a signed-in user ID (401 otherwise). Public dry runs and plan diagnostics retain their existing responses. Inactive plans return the existing 400 validation response. Successful checkout retains `{ id, shortUrl }`.

Checkout saves a pending membership and a server-owned payment quote with immutable price, currency, gateway plan, and session-credit benefits. An owned pending checkout for the same plan is reused. An existing active/paused/halted membership, another pending plan, or changed gateway pricing returns 409. The provider plan's amount, currency, interval, and frequency must match the advertised plan before creation. The billing agreement remains **one cycle** (`total_count: 1`); no automatic-renewal period is introduced. Concurrent gateway creation can leave an unused provider subscription, but only the persisted winner is returned to the customer.

With `PAYMENT_EVENTS_ENABLED=true`, verified `subscription.charged` events atomically record the captured payment, grant the saved credits once per payment, and update VIP access. Activation alone does not grant unpaid benefits. The handler validates subscription ownership, provider plan, captured status, amount, currency, and billing period against the saved quote. Unknown or legacy subscriptions without a quote are skipped for manual reconciliation. Do not backfill ownership or prices from webhook notes. Unexpected additional charges on the single-cycle agreement require reconciliation rather than automatic extra credits.

Cancellation, pause, pending, halt, resume, and completion events update bound memberships. Provider event timestamps guard against older status replays; cancellation cannot be undone by delayed activation. Cancellation preserves previously granted credits. `credits.total` from `/api/memberships/me` now reflects the actual remaining user balance used by credit bookings. Client session updates read entitlements from the database, never client-supplied values.

Webhook signatures use timing-safe comparison. Existing success `{ ok: true }`, signature-mismatch 401, invalid-payload 400, and missing-secret 500 contracts remain. With side effects enabled, application failures now return 500 `{ ok: false, error: 'apply-error' }` so Razorpay can retry. The existing environment gate remains off unless explicitly configured. Invoice failure after a committed grant is retried without duplicating credits. Current-schema invoice lookup tolerates the optional legacy `invoiceUrl` column being absent.

Before enabling production payments, configure the matching Razorpay mode and webhook URL, subscribe to the subscription lifecycle events, and verify a test charge, replay, cancellation, and invoice through the deployed handler. Keep old subscriptions and unmatched/extra charges on a reconciliation list. Booking credits, premium audio, community access, and refreshed sessions check current membership status and expiry rather than trusting a cached VIP flag. Manual VIP accounts without subscriptions retain their existing access.

No database migration is required. Code rollback is a revert; keep any already-recorded payments, membership quotes, and credit grants for reconciliation rather than deleting payment history.

## Lost browser callback recovery

The same gated, signed `payment.captured` handler now finalizes server-owned booking, program, course, and store purchases using the existing transactional finalizer. It validates the captured amount and currency inside the fulfillment transaction and resolves ownership from the saved payment or its booking, never webhook notes. Unknown gateway orders are acknowledged without creating guessed records. Membership charges stay on the subscription-specific path.

Browser verification and webhook delivery can race safely: one payment ID fulfills once, counted inventory decrements once, and invoice failures retry after commit without repeating purchase effects. A webhook does not save its event signature as a browser callback signature. The legacy identifier-only invoice event retains its response and does not grant purchase access. Stock, payment, and ownership failures remain retryable through the enabled webhook's documented 500 response and require operational reconciliation where appropriate.
